# Learning integration

Code paths are relative to `app/src/main/java/app/peekturn/reader/` unless they name a repository-level file.

`learning/ExplanationClient.kt` owns provider requests, structured-output compatibility and clipping Readium's selected-text snippets to the [product context window](SPEC.md#selection-context). Requests to `api.openai.com` use strict JSON schema mode; other hosts, including DeepSeek and custom compatible endpoints, use JSON object mode. Both paths require application validation; host selection does not guarantee model support.

Reader-Activity-owned `learning/LearningSession.kt` owns in-flight work and a small in-memory copy of validated answers; it closes when that Activity is destroyed, but the persisted cache survives. App-scoped `learning/ExplanationCache.kt` owns the durable answer store: 15-day absolute completion TTL, 1 GiB LRU budget, 512 KiB per-record ceiling, atomic opaque-keyed writes and a clear generation. `ExplanationRequest` defines the exact identity, including book id, chapter resource key, provider-clipped context, titles, language and provider configuration; no API key is part of the key. When both before and after context are empty, `hasContextEvidence` is false and `LearningSession`/`ExplanationCache` skip memory and disk reuse entirely; otherwise the normal canonical hash applies. `LearningSession.open` reads the disk cache before requesting, `retry` removes the old entry first, and a clear from Settings invalidates both disk and the session's memory. `ExplanationValidation.kt` shares the parser's completeness/size rules so only a validated answer can be persisted or decoded. `MainActivity` wires the Settings usage/clear row to `AppGraph.explanationCache`. `LearningPopup` resolves the language from `LocalConfiguration` and supplies it explicitly on open/retry. `ExplanationParser` validates example objects before publishing them; `ExplanationExample.spokenText` isolates English speech from translated display copy. `ExplanationClient` and the parser attach an app-owned `ExplanationFailureCategory` to failures; `LearningSession` exposes the category instead of provider text, and `LearningPopup.explanationFailureMessage` maps each category to localized English or Chinese copy. Dictionary tabs do not restart same-lookup work. Dismissal cancels unfinished work; Retry bypasses successful-answer reuse.

`reader/SelectionSession.kt` owns the native selection lifetime and the actual gesture boundary: the pointer's hold start and end, the token that owns asynchronous native reads, the selection each release ended with, and the identity already explained. Automatic explanation is eligible only for a release the app actually observed, and only for the identity that release read recorded when it is usable and is not the one already explained, so a held pointer, an obsolete read, a selection that never finished its gesture or an unchanged selection can never start a request; the observed release is the boundary, not an elapsed delay. Only `ACTION_UP` is an observed release: a cancelled gesture stream (a system gesture or another window taking the touch) can arrive while the finger is still down, so it ends the gesture without making its range explainable. Because Readium's release-time read is an asynchronous WebView round trip, the released selection is read under a bounded budget: only repeated reads that agree count as confirmed, a native range that keeps moving is unconfirmed, an empty read means nothing is selected, and a read that never answers is unavailable. Automatic explanation acts only on a confirmed range, so an unconfirmed, empty or unavailable release records no released range at all. Two invariants hold: an automatic explanation may only use the identity recorded for the released gesture, so once that identity is recorded no later read can substitute a different one, and every read is re-validated against the gesture token, the navigator and the reader's lifecycle before it can be used, with any newer gesture, session, page or popup cancelling it. Adjusting keeps the native selection while the recorded explained identity prevents reopening the old highlight. The physical pointer lifetime is separate from selection state: the hold start and end follow the real touch stream, `cancelGesture` (a cancelled gesture stream or a reader pause) ends a held gesture without recording an observed release, `clear()` bumps the session token and drops the released/explained state without ending a held gesture, source input may end the session only with the pointer up, and a debounced location change cannot clear a selection that a held gesture still owns. Explicit Explain, Dictionary and Copy always resolve the live native selection and never act on a remembered range: they use the same bounded read, validated against the session token, the navigator and the reader's lifecycle but not against a held pointer, so a finger resting on the page cannot turn the user's own command into a failed read, and an empty or unanswerable read reports a truthful message while leaving the native selection intact. The range recorded when the gesture was released only gates automatic explanation.

The native action mode remains alive in both Quick Explain modes because Chromium uses its creation/recreation as a selection signal. `readerSelectionActions(quickExplain)` supplies no items when Quick Explain is enabled, hiding the floating toolbar without finishing the action mode or clearing the native range. With Quick Explain disabled it supplies Explain, Dictionary and Copy. Menu visibility must not become a second gesture-release or lookup-eligibility rule.

Dictionary packaging uses a `.dict` extension to preserve precompressed gzip bytes through Android asset packaging. `tools/build_dictionary.py` owns rebuilding; the [dictionary notices](../../../THIRD_PARTY_NOTICES.md#ecdict-offline-dictionary) own provenance and rebuild instructions.
